# C++ 工程规范

## 1. 适用范围与规范读取

本规范适用于项目中的 C++ 源码、静态库、动态库、命令行工具、桌面模块和跨语言边界。

涉及 C++ 文件时，必须先读取本规范以及直接相关的 CMake、并发、日志、验证、安全和代码 Review 规范。嵌入式 C++ 任务必须同时读取 [嵌入式开发](embedded.md)；冲突时以更具体的嵌入式约束为准。

## 2. 基本原则

- 优先使用值语义、RAII、类型安全和编译期检查。
- 默认选择最简单、可验证的同步实现；只有测量证明需要时才引入并发、模板元编程或复杂抽象。
- 禁止依赖未定义行为、实现细节、编译器偶然行为或未记录的平台扩展。
- 每个内存、文件、锁、线程、句柄、回调和异步任务都必须有明确所有者和生命周期。
- 代码行为、错误处理和边界条件必须能够被测试或静态检查验证。

## 3. 语言版本与工具链

- 由项目构建配置明确声明 C++ 标准；新项目优先 C++20，使用 C++23 前确认工具链、目标平台和依赖支持。
- CMake 使用 `target_compile_features` 或目标级 `CXX_STANDARD`，不混用不同标准或私有扩展。
- 源文件使用 UTF-8；项目自有目标启用 `-Wall -Wextra -Wpedantic` 或 MSVC `/W4`。
- CI 对项目自有目标启用 `-Werror` 或 `/WX`；第三方目标不得继承警告和 warnings-as-errors。
- `NOLINT`、`#pragma warning(disable: ...)` 和编译器禁用参数必须限定到最小范围并说明原因。

## 4. 目录、模块与依赖方向

推荐按职责组织：

```text
app/cpp/
├── include/<project>/
│   ├── domain/
│   ├── services/
│   └── public/
├── src/
│   ├── domain/
│   ├── services/
│   └── platform/
└── tests/
```

- 领域层不得直接依赖 UI、操作系统、网络库或具体日志实现。
- 平台能力通过接口或适配器隔离；应用入口只负责启动和模块组装。
- 公共头文件只暴露稳定且必要的 API；内部实现不得通过公共头文件泄露。
- 使用 include-what-you-use，不能依赖传递包含；不在公共头文件中使用 `using namespace`。
- 依赖方向保持单向：公共接口与领域模型 → 服务与平台适配 → 应用入口和外部系统。

## 5. 命名与格式

- 命名空间使用 `snake_case`。
- 类型、类、结构体、枚举和概念使用 `PascalCase`。
- 函数、方法、局部变量和参数使用 `camelCase`。
- 文件名使用小写 `snake_case`；宏仅用于必要的平台适配，使用项目名前缀和 `SCREAMING_SNAKE_CASE`。
- 格式由项目 `.clang-format` 统一管理，提交前运行项目已有格式检查或 `clang-format --dry-run --Werror`。

## 6. 类型、初始化与所有权

- 局部变量默认 `const`，使用花括号初始化，禁止未初始化读取和隐式窄化转换。
- 使用 `enum class`、`std::optional`、`std::span` 和 `std::string_view` 表达明确语义，并确认视图的生命周期。
- 不使用 `void*`、C 风格强制转换、未约束的 `reinterpret_cast` 或整数保存指针。
- 默认使用栈对象和值类型；独占所有权使用 `std::unique_ptr`。
- 只有确实存在共享生命周期且无法明确所有权时使用 `std::shared_ptr`，并说明共享原因；`std::weak_ptr` 仅用于打破已确认的所有权环。
- 裸指针和引用默认表示非拥有关系，接口必须说明可空性和生命周期。
- 不使用 `new`/`delete` 管理业务对象；资源必须由 RAII 包装。
- 不返回指向局部变量、临时对象或已释放资源的引用、指针或视图。
- 回调必须绑定注销或所有者生命周期；异步任务禁止无条件捕获裸 `this`。

## 7. 类与接口设计

- 类保持单一职责，构造函数建立不变量，公共接口最小化。
- 遵循 Rule of Zero；只有管理非 RAII 资源时才手动定义特殊成员函数。
- 需要多态删除时基类析构函数为 `virtual`；覆盖虚函数必须使用 `override`。
- 不在构造函数中启动无法回收的线程、长时间 I/O 或依赖对象已完全注册的回调。
- 模板和概念必须有明确约束；复杂模板只有在减少重复且可测试时使用。
- 不在头文件中放置与模板无关的大段业务实现。

## 8. 错误处理

- 错误必须可定位、可传播、可测试，不能只返回布尔值或打印后继续。
- 使用项目统一错误类型；支持时可使用 `std::expected` 表达可预期失败。
- 不使用异常作为普通业务分支。启用异常时不得跨 C ABI、设备回调、ISR、线程入口或不支持异常的第三方边界传播。
- 禁用异常时，所有失败路径使用明确错误类型或状态码，调用方不得静默忽略返回值。
- `assert` 只用于程序员不变量，不能替代输入校验、权限检查或运行时错误处理。
- 错误消息不得包含密钥、凭据、隐私、完整路径、内部堆栈或未脱敏输入。

## 9. API、ABI 与跨语言边界

- 公共 API 明确参数所有权、可空性、线程安全、错误语义和生命周期。
- C++ 类型、异常、STL 容器和编译器私有类型不得无约束地跨稳定 ABI 或 C ABI 边界。
- C ABI 使用固定宽度整数、显式长度和明确释放函数；禁止跨运行库释放内存。
- IPC、插件、持久化和跨进程边界使用版本化、可演进的数据结构，不直接序列化 C++ 对象内存布局。
- 动态库公共符号使用显式导出宏，默认隐藏内部符号；ABI 变更必须记录兼容策略。
- 外部输入进入领域层前校验长度、范围、编码、版本和权限。

## 10. 并发、日志与安全

遵循 [并发与线程](concurrency.md) 和 [日志与终端输出](logging.md)：

- 默认单线程；引入线程、线程池、协程或并行算法前定义目标并用基准证明收益。
- 线程、队列、重试、缓存和任务数量必须有界；禁止不可回收的 `detach` 线程。
- 锁范围最小，锁内禁止阻塞 I/O、回调、长计算和未知外部调用；多锁规定统一顺序。
- 使用统一日志适配器记录组件、事件、操作 ID、阶段、结果、错误码和耗时。
- 不在锁内、实时线程、ISR、析构函数和不允许阻塞的路径执行日志 I/O。
- 高频日志限频、采样或汇总；日志入口执行敏感信息脱敏和多行转义。
- 禁止缓冲区越界、Use-after-free、Double-free、数据竞争、整数溢出和未定义行为。
- 外部命令、动态库、插件和反序列化采用允许列表和最小权限；不执行字符串拼接命令或 SQL。

## 11. 构建与依赖

遵循 [CMake 规范](cmake.md)：

- 使用 target 级配置，依赖明确标记 `PRIVATE`、`PUBLIC` 或 `INTERFACE`。
- 第三方依赖使用锁定版本或可复现来源，记录用途、许可证和平台兼容性。
- 构建必须支持项目需要的 Debug、Release 和 Sanitizer 配置；生成文件、缓存和临时日志不得提交。
- CMake 配置失败、警告或生成器不一致不得被脚本静默忽略。

## 12. 静态检查、Sanitizer 与测试

- 按目标平台启用 `clang-format`、`clang-tidy`、`cppcheck` 和 MSVC `/analyze` 等可用检查。
- 按风险启用 AddressSanitizer、UndefinedBehaviorSanitizer、ThreadSanitizer；Sanitizer 不能替代硬件和平台测试。
- 单元测试覆盖领域逻辑、边界和错误；集成测试覆盖文件、网络、设备和跨语言边界。
- 并发测试使用屏障、条件变量、测试时钟和可控信号，不依赖固定睡眠或偶然调度。
- 性能承诺必须记录硬件、编译器、构建类型、数据规模和并发配置。
- 提交前按项目实际支持的 preset 或命令执行配置、构建、测试、格式化和静态检查，并如实记录未覆盖范围。

## 13. Review 检查项

Review C++ 改动时至少检查：

- 是否先读取本规范及直接相关专题规范。
- 模块依赖、公共头文件和 API/ABI 是否清晰稳定。
- 所有权、RAII、移动/复制语义、生命周期和异常安全是否明确。
- 是否存在裸内存管理、悬空引用、未定义行为、越界、数据竞争或整数溢出。
- 线程、锁、任务取消、超时和关闭生命周期是否安全。
- CMake target、依赖、警告、Sanitizer、静态检查和测试是否覆盖风险。
- 日志是否可回溯、有限频、可脱敏且不会阻塞关键路径。
- 每次 Review 后按 [代码 Review 规范](code-review.md) 生成日期命名报告。
