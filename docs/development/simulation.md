# 仿真、Sim2Real 与硬件在环规范

## 1. 适用范围与规范读取

本规范适用于机器人仿真、具身智能训练、运动规划验证、Software-in-the-Loop（SIL）、Hardware-in-the-Loop（HIL）、回放测试和实机迁移。

涉及仿真任务时，先读取本规范，并按范围读取 [具身智能与机器人系统](robotics.md)、[安全工程](safety.md)、[嵌入式开发](embedded.md)、[C++ 开发](cpp.md)、[并发与线程](concurrency.md)、[日志与终端输出](logging.md)、[验证](verification.md) 和 [代码 Review](code-review.md)。仿真器、物理引擎、机器人模型、硬件 SDK 和场景资源使用项目锁定版本，不凭记忆构造参数或 API。

仿真通过只能证明在声明的模型、场景、参数和故障范围内通过，不能替代实机安全验收。

## 2. 仿真层级与适用目标

| 层级 | 主要用途 | 不能证明 |
| --- | --- | --- |
| 模型级（MIL） | 算法、控制律和数学模型验证 | 软件实现、实时性和硬件时序 |
| 软件在环（SIL） | 真实软件接口、状态机、回放和回归 | 目标硬件、驱动和物理执行器安全 |
| 硬件在环（HIL） | 目标控制器、通信、时序、故障响应 | 全部真实机械、环境和人员风险 |
| 受控实机 | 真实传感器、执行器、环境和 Sim2Real 验证 | 未覆盖的极端环境与长期现场风险 |

- 每个测试声明层级、目的、模型假设、输入范围、通过标准和未覆盖范围。
- 不得用 MIL/SIL 结果替代 HIL、实机或安全验证；不同层级的指标不能直接混用。
- 仿真接口与实机接口保持一致，平台差异通过适配层隔离并纳入测试。

## 3. 版本、来源与可复现性

- 记录仿真器、物理引擎、机器人模型、场景、插件、依赖、地图、传感器参数和工具链版本。
- 每次运行绑定 Git 提交、配置文件、模型/策略版本、数据集版本、随机种子、操作系统和硬件资源。
- 场景、机器人模型、纹理、地图和标定文件不得从不可追溯的本地路径隐式加载。
- 随机测试固定种子可复现；随机种子变更视为测试输入变化，必须记录。
- 运行输出包含配置快照、指标、事件日志、失败样本和环境摘要；大文件使用可追溯的资产引用。
- 不能复现时说明缺失的版本、硬件、随机源或外部服务，并将结论标记为未验证。

## 4. 物理、传感器与执行器模型

- 记录质量、惯量、质心、关节限位、摩擦、间隙、阻尼、执行器带宽、饱和、延迟和控制周期。
- 传感器模型包含采样率、时间戳、噪声、偏置、漂移、量化、延迟、丢帧、视野、遮挡和失效模式。
- 执行器模型包含命令延迟、反馈延迟、限幅、死区、饱和、热行为、故障和安全停止响应。
- 单位、坐标系、关节顺序、零位、安装外参和时钟基准与实机一致，变更必须有校准证据。
- 物理引擎简化、碰撞模型、接触参数和求解器设置必须记录；不以视觉上合理替代动力学验证。
- 对不确定参数给出范围或分布，并通过敏感性分析确认结论是否依赖单一理想参数。

## 5. 场景与测试用例

- 场景使用稳定 ID、日期命名、版本和来源；任务目标、初始状态、环境约束、障碍物、人员和终止条件明确。
- 测试用例包含前置条件、输入、随机种子、运行时限、期望安全状态、指标、阈值和失败证据。
- 正常、边界、极端、长时间、随机扰动和故障场景分开统计，不得只报告平均成功率。
- 覆盖传感器失效、通信延迟、执行器饱和、控制器崩溃、模型输出越界、环境变化和人工接管。
- 场景修改必须保留历史版本或记录变更原因，避免通过修改场景掩盖回归失败。

## 6. SIL 与回放

- SIL 使用与目标系统一致的接口、状态机、错误码和日志事件模型；禁止为仿真单独绕过安全监督。
- 回放数据保留原始时间戳、坐标系、单位、设备标识、校准、软件/模型版本和数据质量。
- 回放支持确定性重放和逐步诊断；不能重放的随机、外部服务和硬件行为必须显式标记。
- 结果比较不仅包括成功/失败，还应包括轨迹、误差、延迟、控制周期、约束违规、资源和安全状态。
- 回放失败时保留最小可复现输入、配置、日志和版本引用，不覆盖原始失败样本。

## 7. HIL 设计

- HIL 明确真实部件、模拟部件、通信接口、时钟来源、采样周期、最大延迟和实时预算。
- HIL 仿真器必须在目标周期内产生输入；超时、过载、丢帧、时钟漂移和接口断开都有确定行为。
- 目标硬件使用真实编译配置、固件、驱动、内存布局和通信协议；测试替身不得掩盖真实边界。
- HIL 设备、线缆、电源、负载、固件、仿真器和脚本版本可追溯，运行前检查急停、限流和安全隔离。
- HIL 结束时停止命令、释放设备、关闭电源或进入安全状态；不得遗留危险输出或后台任务。
- HIL 结果记录目标板、固件、仿真器、接口、周期、抖动、队列、故障响应和导出日志。

## 8. Sim2Real 迁移

- 明确仿真到实机的映射：坐标、单位、标定、控制周期、延迟、噪声、执行器限制、通信和安全约束。
- 对动力学、接触、传感器、时钟、网络、环境和人员因素建立差异清单，并为高风险差异设计实机验证。
- 迁移顺序遵循仿真离线 → SIL → HIL → 空载低速实机 → 受限载荷 → 目标场景，逐级记录放量条件。
- 未校准、未验证或超出仿真边界的策略和参数不得直接用于高能量或有人环境。
- Sim2Real 报告必须包含失败样本、差异原因、临时补丁、最终参数和仍未验证的边界。

## 9. 安全与故障注入

- 所有仿真和 HIL 场景遵循 [安全工程](safety.md) 的安全状态、急停、保护停止和恢复要求。
- 故障注入至少覆盖传感器冻结/漂移/断连、时间戳错误、执行器卡滞/饱和、通信丢包/乱序、供电异常、任务卡死和模型输出越界。
- 故障注入记录注入时刻、对象、参数、预期状态、实际状态、响应时间、日志证据和恢复结果。
- 注入工具必须有权限和范围限制，禁止在未隔离的实机或生产设备上执行危险注入。
- 仿真器、HIL 或测试脚本故障时，不能伪造被测系统通过；测试本身失败应单独报告。

## 10. 指标与验收

指标按任务定义，至少考虑：任务成功率、失败类型分布、轨迹/姿态误差、碰撞和约束违规、控制周期、端到端延迟、丢帧率、资源占用、能耗、温度、恢复时间和安全状态响应时间。

- 指标给出数据范围、单位、统计方法、分位数或置信区间；不能只给单次或平均值。
- 通过阈值、失败阈值、不可接受事件和人工复核条件必须预先定义。
- 模型、场景、配置或硬件变化后重新生成基线，不得沿用不可比结果。
- 验收记录实际命令、环境、版本、种子、输出位置、失败样本和未覆盖范围。

## 11. 性能、并发与资源

- 仿真运行数量、并发任务、队列、缓存、日志和输出文件必须有界；不能因批量实验无限创建进程或文件。
- 只有基准证明需要时才并行仿真；记录 CPU/GPU、内存、显存、线程数、批大小和调度配置。
- 实时 HIL 不得使用会导致周期失控的阻塞日志、无界分配或不可控网络调用。
- 仿真失败、超时、资源耗尽和日志写入失败必须区分，并保留可诊断的失败摘要。
- 关闭时等待或取消所有仿真、渲染、通信、记录和子进程，确认无遗留资源。

## 12. 验证与 Review 检查项

仿真 Review 至少检查：

- 层级、目的、模型假设、版本、随机种子和可复现证据是否完整。
- 单位、坐标、时间、标定、物理参数、传感器和执行器模型是否与实机一致或差异已记录。
- 正常、边界、极端、故障和长时间场景是否覆盖，是否预先定义指标和阈值。
- SIL/HIL/实机边界是否清楚，HIL 时序、过载、急停、断开和资源回收是否验证。
- Sim2Real 差异、放量条件和失败样本是否记录，是否存在用仿真结果替代安全验收的结论。
- 日志是否能关联运行、故障、配置和回放，敏感信息是否脱敏。
- 每次 Review 依据 [代码 Review 规范](code-review.md) 生成日期命名报告，区分事实、推断和未验证范围。
