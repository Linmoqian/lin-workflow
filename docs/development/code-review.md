# 代码 Review 规范

## 1. 目标与边界

- Review 用于发现本次变更的问题、仓库现存问题和潜在风险。
- Review 默认只读，不直接修改代码、配置、文档或 Git 历史；修复应作为独立任务完成，并重新 Review。
- Review 开始时明确审查对象、基准版本、审查范围和未审查范围。
- 审查提交或 Pull Request 时，区分本次变更引入的问题、仓库原有问题和未证实的潜在风险。

## 2. 规范依据

每次 Review 开始前必须实际读取并记录：

1. `AGENTS.md`
2. `CLAUDE.md`
3. `TODO.md`
4. 与变更相关的专题规范
5. 当前目录及子目录中的更具体规范
6. 相关接口、测试、构建和架构文档

按变更内容选择专题规范，至少覆盖适用的前端、C++、嵌入式、Rust、HarmonyOS、Python、CMake、并发、接口、日志、验证、Git、GitHub、项目地图和写作规范。不得只凭记忆或代码风格印象完成 Review。

## 3. Review 流程

### 3.1 建立基线

先记录工作区、分支、当前提交、近期提交和变更统计：

```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git log -10 --oneline
git diff --stat
```

审查提交或 Pull Request 时，额外确认基准提交和完整差异：

```powershell
git diff <base>...<head> --stat
git diff <base>...<head>
```

已有未提交改动属于工程师的工作，必须与本次审查范围分开，不得覆盖、清理或混入结论。

### 3.2 深度检查

按照以下顺序检查，并将实际检查结果写入报告：

1. 规范符合性：目录、命名、依赖、注释、接口、并发和工程流程。
2. 功能正确性：正常路径、边界条件、错误处理、状态转换和数据一致性。
3. 安全性：权限、输入校验、路径处理、敏感信息、命令执行和依赖风险。
4. 架构与可维护性：模块边界、依赖方向、重复逻辑、文件规模和职责分离。
5. 性能与并发：阻塞操作、锁、异步任务、资源释放和潜在泄漏。
6. 测试与验证：测试覆盖、失败路径、构建、静态检查和回归范围。
7. 接口与文档：实现、类型、测试和接口文档是否同步。
8. 构建与发布：CI、版本、构建产物、配置和回滚影响。
9. 日志可回溯性：操作链、关联 ID、状态、耗时、错误上下文、脱敏、采样和高频输出。

### 3.3 执行验证

- 优先使用项目已有的格式化、静态检查、测试和构建命令。
- 只报告实际执行过的命令和结果；不得把静态推断写成已验证结果。
- 命令通过时记录关键结果；失败时记录错误摘要和影响；未执行时说明原因、替代检查和未覆盖风险。
- 不因 Review 强行引入新测试框架、新工具或无关依赖。

## 4. 问题与风险

### 4.1 已确认问题

已确认问题必须有代码、配置、测试、构建或命令输出作为证据。每条问题至少记录：编号、严重性、状态、文件位置、事实描述、违反的规范、影响、验证结果和修复建议。

严重性分级：

- `Critical`：安全漏洞、数据损坏、严重信息泄露或明确阻塞发布。
- `High`：核心功能错误、接口破坏、权限绕过或高概率生产故障。
- `Medium`：重要边界缺陷、明显规范违例、错误处理缺失或测试不足。
- `Low`：非阻塞的可维护性、风格或局部技术债。
- `Info`：信息记录或改进建议，不构成缺陷。

### 4.2 潜在风险

潜在风险是基于当前证据的推断，不能写成已确认问题。每条风险至少记录：编号、严重性、可信度、风险对象、事实依据、推断内容、触发条件、影响范围、建议验证方式和缓解措施。

报告必须明确区分：

- `事实`：已从代码、文档、命令或测试中观察到。
- `推断`：基于事实推导出的可能后果。
- `未验证`：当前环境无法确认的结论。

## 5. Review 报告

每次 Review 完成后必须在 `docs/review/` 创建一份 Markdown 报告。文件名遵循项目日期命名规范：

```text
docs/review/YYYY-MM-DD-code-review-主题名.md
```

报告至少包含以下内容：

```markdown
# 代码 Review 检查报告

## 1. 基本信息

- 审查日期：
- 审查对象：
- 分支：
- 基准提交：
- 当前提交：
- 审查范围：
- 未审查范围：

## 2. 规范依据

列出本次实际读取的 AGENTS、CLAUDE、专题规范和其他依据。

## 3. 审查方法与验证

列出实际执行的命令、测试、构建、静态检查和人工检查结果。

## 4. 审查结论

说明通过、有条件通过或不通过，并给出依据。

## 5. 仓库问题

| 编号 | 严重性 | 状态 | 位置 | 事实、规范与证据 | 影响 | 修复建议 |
| --- | --- | --- | --- | --- | --- | --- |

## 6. 潜在风险

| 编号 | 严重性 | 可信度 | 风险对象 | 事实与推断依据 | 触发条件 | 建议验证 |
| --- | --- | --- | --- | --- | --- | --- |

## 7. 规范符合性检查

记录各专题规范的通过、不通过、未覆盖和未验证项。

## 8. 未覆盖范围

说明未运行的测试、未检查的模块、不可用的环境和证据缺口。

## 9. 修复优先级

按 Critical、High、Medium、Low 排列后续行动。

## 10. 后续跟踪

记录修复提交、复查日期、复查结果和仍未关闭的风险。
```

没有发现问题时也必须生成报告，并明确写出“未发现问题”及未覆盖范围。报告不得删除历史问题；修复后标记状态并保留原始记录。

## 6. 结论规则

- 没有发现问题，不等于仓库不存在风险。
- 测试通过不等于规范检查完成。
- 代码能够构建不等于功能完成或可以发布。
- 只有在证据覆盖充分时，才能写“通过”。
- 证据不足时必须写“未验证”或“无法判断”。
- 报告遵循写作规范，使用事实、推断和未验证状态的明确标记。
- 日志专项检查必须说明是否能通过关联 ID 还原关键执行路径，以及是否存在敏感信息泄露、刷屏、采样缺失或 Debug 输出未关闭。
