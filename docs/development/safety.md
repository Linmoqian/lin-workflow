# 机器人与具身系统安全工程规范

## 1. 适用范围与边界

本规范适用于具身智能、机器人、动力执行器、移动设备、机械臂、无人设备和人机协作系统的软件安全工程。

涉及安全相关任务时，先读取本规范，并按实现范围读取 [嵌入式开发](embedded.md)、[C++ 开发](cpp.md)、[并发与线程](concurrency.md)、[日志与终端输出](logging.md)、[验证](verification.md)、[代码 Review](code-review.md) 和适用的硬件、法规、客户标准。项目若涉及医疗、汽车、航空、工业安全或人员伤害风险，必须由具备资质的人员确认适用标准、等级、验证和签署要求。

本规范不能把未经评估的系统声明为安全，也不能用软件日志、模型置信度或仿真结果替代物理防护、急停和风险评估。

## 2. 安全目标与风险边界

- 明确保护对象：人员、设备、环境、数据和任务目标；记录不可接受的伤害、损坏和失控状态。
- 为每个系统定义安全边界、允许的能量、速度、力、温度、工作空间、载荷和操作环境。
- 安全目标必须可验证，例如“通信丢失后在规定时间内停止危险运动”，不得只写“提高安全性”。
- 安全监督的默认策略是拒绝危险命令、进入可预测安全状态并通知操作者；不能依赖上层模型自行判断。
- 安全约束优先级高于任务完成、性能、吞吐和用户便利性。

## 3. 危险分析与安全论证

在设计、硬件变化、模型变化、部署环境变化和重大软件变更前执行危险分析：

1. 列出危险源、危险事件、暴露人员、触发条件和后果。
2. 评估严重度、发生概率、可避免性或项目采用的等价风险维度。
3. 为不可接受风险分配安全需求、预防措施、检测措施和缓解措施。
4. 将每条安全需求映射到设计、实现、测试和证据。
5. 记录残余风险、假设、责任人、接受人和复审日期。

可使用 FMEA、故障树（FTA）、事件树、危害日志或等效方法，但必须记录版本、范围、假设和结论。模型、传感器、通信、供电、执行器、人因、环境和第三方依赖必须纳入分析；不得只分析正常软件路径。

## 4. 安全状态与状态转换

至少定义以下状态及其进入、退出和允许动作：

| 状态 | 含义 | 典型允许动作 |
| --- | --- | --- |
| `normal` | 正常任务运行 | 受约束的任务动作 |
| `degraded` | 功能受限但仍可控 | 降速、降载或有限任务 |
| `protective_stop` | 检测到风险，停止危险动作 | 诊断、人工确认、受限复位 |
| `emergency_stop` | 紧急停止，保持锁定 | 仅允许安全复位流程 |
| `fault` | 故障待处理 | 记录、隔离、维护 |
| `maintenance` | 授权维护状态 | 受控诊断和维修动作 |

- 状态转换必须由明确事件触发，并记录来源、时间、原因和结果。
- 保护停止和急停不得自动恢复危险运动；恢复前重新检查人员、设备、传感器、限位和任务状态。
- 复位是幂等操作，必须避免重复上电、重复动作或恢复过期命令。
- 安全状态的失效保护方向必须明确：看门狗、通信中断、供电异常、控制器崩溃和安全监督失联时进入哪个状态。

## 5. 急停、保护停机与物理防护

- 急停必须有独立、可触达、可测试的硬件路径；软件按钮不能替代硬件急停，除非风险分析明确允许并有等效防护。
- 急停应切断或抑制危险能量，控制制动、继电器、驱动器使能、保持力和惯性运动，并验证停止时间和停止距离。
- 急停信号应具备冗余、监测、锁存和防误复位设计；复位不得自动重新启动危险动作。
- 保护停机用于可控的风险降级，急停用于需要立即停止或无法保证可控减速的危险情况；两者不可混用。
- 软件安全监督、硬件限位、机械限位、护栏、联锁和电源隔离各自的作用与失效模式必须记录。
- 每次运行前检查急停、限位、制动、护罩、联锁、看门狗和安全输入；测试结果可追溯。

## 6. 安全约束与运行时监控

- 所有运动命令通过集中安全监督，校验速度、加速度、力、力矩、功率、温度、载荷、工作空间、碰撞距离和命令有效期。
- 约束使用安全默认值和上限；配置变更需权限、版本和审计记录，禁止运行时无审计地放宽限制。
- 传感器数据过期、冲突、越界、失真或质量不足时，进入明确的降级或停止状态。
- 通信心跳、控制反馈、执行器响应、供电、温度、内存、任务和时钟同步必须有超时和失效行为。
- 模型或规划器输出必须经过规则、几何、动力学和安全约束检查；模型置信度不能单独作为安全证明。
- 安全监控自身必须有健康检查、看门狗、故障注入和失联处理，不能只监控被控对象。

## 7. FMEA 与故障树要求

FMEA 至少包含：组件或功能、失效模式、原因、局部影响、系统影响、检测方式、安全响应、严重度、发生概率、可检测性、责任人和验证证据。

故障树至少：

- 顶事件定义为明确的危险结果，而不是“系统异常”。
- 使用可审查的逻辑门、基本事件、公共原因和独立性假设。
- 分析传感器失效、执行器卡滞、软件错误、时钟异常、通信丢失、供电异常、人因和环境因素。
- 对单点故障、潜伏故障、共因故障和故障组合给出检测或缓解方案。
- 任何“不会发生”“不可能同时发生”或“由操作员处理”的假设都要记录证据和边界。

FMEA/FTA 的结论必须转化为代码、配置、硬件或操作需求，并进入测试与 Review 清单。

## 8. 人员、环境与人工接管

- 明确人员可进入区域、最小安全距离、速度/力限制、可见性、通信方式和人工接管优先级。
- 人工接管命令必须可辨识、可测试、不可被普通任务覆盖，并记录操作者和结果。
- 地面、光照、温度、噪声、电磁、网络、障碍物、载荷变化和异常环境必须纳入风险边界。
- 无人或远程运行必须定义失联、延迟、视频不可用、操作者退出和现场人员进入时的安全行为。
- 不得以“用户应当注意”替代可验证的物理和软件防护。

## 9. 故障响应、恢复与诊断

- 每类故障定义检测、隔离、状态转换、告警、停止、恢复、人工确认和不可恢复路径。
- 自动恢复只允许用于已证明不会扩大风险的故障；恢复前重新确认安全条件和命令有效期。
- 任务、控制器、设备和系统重启后必须从实际状态重建，不得重放过期或未确认的危险命令。
- 故障日志遵循 [日志与终端输出](logging.md)，包含固件/软件/模型版本、设备标识、阶段、状态、错误码、时间基准和关键状态摘要，禁止敏感信息。
- 故障记录必须有容量上限、校验、持久化策略和导出方式；日志丢失本身应可检测。

## 10. 故障注入与验证

至少验证：

- 传感器断连、冻结、漂移、偏置、噪声、越界、时间戳错误和数据冲突。
- 执行器失效、卡滞、饱和、反馈不一致、过温、过流和驱动器失联。
- 通信延迟、丢包、乱序、重复、带宽耗尽、心跳超时和错误命令。
- 控制器崩溃、任务卡死、队列满、栈/堆耗尽、时钟跳变、看门狗复位和供电中断。
- 模型加载失败、输出越界、规划无解、地图过期、环境突变和人工接管。
- 急停、保护停止、限位、联锁和恢复流程的实际响应时间与状态。

测试分层使用主机、SIL、HIL、目标板和受控实机；先低能量、低速度、空载和隔离环境，再逐步放量。每项测试记录注入方式、预期安全状态、实际状态、响应时间、日志证据和未覆盖范围。

## 11. 变更、发布与运行前检查

- 影响传感器、执行器、规划、控制、模型、坐标、限值、急停或安全状态的变更必须重新评估风险。
- 发布前确认代码、配置、固件、模型、标定、硬件、工具链和安全分析版本一致。
- 发布包包含安全配置、兼容矩阵、急停/复位说明、已知风险、验证证据和回滚方案。
- 现场运行前检查设备、供电、通信、急停、限位、护罩、空间、人员、任务、日志和版本。
- 任何安全证据缺失、急停不可用、限制未加载或版本不匹配时，禁止进入危险运行状态。

## 12. Review 检查项

安全 Review 至少检查：

- 危险分析、FMEA/FTA、假设、残余风险和安全需求是否有证据。
- 安全状态、急停、保护停止、限位、联锁、看门狗和人工接管是否独立、可测试、不可绕过。
- 传感器、执行器、通信、供电、模型和环境故障是否有确定响应。
- 限值、超时、过期数据、权限、配置变更和恢复路径是否安全默认。
- 故障注入、SIL/HIL、实机、耐久和运行前检查是否覆盖并留存证据。
- 日志能否回溯安全状态和故障原因，且不泄露敏感数据、不阻塞关键路径。
- 结论必须区分已确认问题、潜在风险、假设和未验证项，并按 [代码 Review 规范](code-review.md) 生成报告。
