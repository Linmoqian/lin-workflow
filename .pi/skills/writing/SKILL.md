# 写作规范

## 1. 写作准备

- 动笔前明确目标读者、交付载体、写作范围和需要读者采取的行动。
- 只写任务所需内容；未知、假设和限制应明确标注，不得以推测代替事实。
- 术语首次出现时说明含义；同一概念在全文使用同一名称。

## 2. 事实与引用

- 数据、结论、外部事实和引用应能追溯到可靠来源，链接应指向支持该说法的具体页面。
- 引用应说明来源、时间或版本等必要上下文；示例数据必须脱敏。
- 不伪造引用、链接、数据、实验结果或读者反馈；无法核实的内容应说明未核实状态。

## 3. 结构与表达

- 标题按层级组织，避免跳级；一个标题只表达一个主题。
- 段落围绕单一观点，先给结论或重点，再补充依据、条件和例外。
- 使用短句和具体动词，删除空话、重复、无依据的程度词和无实际信息的总结。
- 仅在确有比较、步骤、映射或选择时使用表格、列表和强调，避免过度格式化。

## 4. 目录、Markdown 与素材

- 文档按主题或交付物建立目录；同一文档的 Markdown、LaTeX 源码、PDF 与素材必须位于同一目录，不按文件格式分别建立全局目录。
- 文档目录和文件名使用小写 kebab-case；文档文件名必须以创建或更新日期开头，格式为 `YYYY-MM-DD-主题名.扩展名`，例如 `2026-08-24-full-issue-risk-review.md`。
- 文档目录使用清晰、稳定的名称；目录日期同样使用 `YYYY-MM-DD`，其中 `assets/` 只存放该文档引用的图片、图表等素材，不创建无内容的目录。
- 同一文档的主文件使用相同的日期和主题名，例如 `2026-08-24-release-notes.md`、`2026-08-24-release-notes.tex` 与 `2026-08-24-release-notes.pdf`；仅存在其中一种格式时，不创建空的同名文件。
- 不使用空格、中文、下划线、混合大小写或模糊日期（如 `today`、`latest`）命名文档；日期变更表示新版本或新文档，不覆盖原有日期记录。
- GitHub Wiki 的稳定页面为保持固定链接，可使用小写 `kebab-case` 且不强制日期前缀；页面顶部必须记录状态、适用版本、维护人、最后复审日期和权威来源。Wiki 的历史报告、会议记录和复盘仍使用日期前缀。
- 每份文档指定唯一可编辑的权威源，默认是 Markdown；以 LaTeX 为排版源时应明确以 `.tex` 为准，不得双向同步。
- 仅在确需排版或 PDF 交付时增加 `.tex` 与 `.pdf`；PDF 为构建产物时应能从同目录源文件再生成，`.aux`、`.log` 等辅助文件不纳入文档目录或版本控制。
- Markdown 保持可读的源文本；代码、命令、路径和标识符使用代码格式，代码块标明语言。
- 表格只承载适合横向比较的简短信息；复杂逻辑使用分段说明或图示。
- 图表必须有标题或图注，说明其表达的结论、数据来源和必要的单位、时间范围或口径。
- 图片应提供准确的替代文本；截图仅用于无法用文字或结构化内容清楚表达的界面与状态。
- 不用图片替代可复制的正文、代码、表格或数据。

## 5. 文档与报告

- 技术文档应包含适用范围、前置条件、操作步骤、预期结果或验收方式，以及必要的失败处理或限制。
- 报告优先给出结论、证据和建议，再说明方法与细节；结论须与证据范围相符。
- 对有风险的操作、破坏性行为、兼容性影响或未验证内容进行显式提示。

## 6. 文档解析与格式转换

- PDF、扫描件、Office、多栏排版、表格、公式和图表等复杂文档，优先使用 [MinerU 官方 API](https://mineru.net/apiManage/docs) 解析；按官方当前限制选择精准解析或 Agent 轻量解析，并按需输出 Markdown、JSON、DOCX、HTML 或 LaTeX。
- 简单文本、Markdown 或 MinerU 不可用时，使用 MarkItDown 或项目已有工具；不为一次性转换从零编写解析器。
- 解析或转换前确认文档已获授权，尤其是个人信息、生物数据、内部资料和受版权保护内容；未授权内容不得上传第三方服务。
- 记录源文件校验和、解析器/模型版本、任务 ID 或 trace ID、输入输出格式、转换时间、输出校验和及失败原因；不得静默覆盖原始文件。
- 转换结果必须人工或机器核验标题层级、表格、公式、图片、引用、页码和链接；格式转换不等于内容事实核验。
- MinerU 所需 Token/API Key、权限或配额不可用时，向工程师请求；密钥不得写入文档、仓库、命令输出或日志。
- 学术文献检索优先使用 [SciVerse 文档](https://sciverse.opendatalab.com/docs)；保存查询、文献标识、证据片段、来源位置、评分和检索时间，关键论断回到原始来源核验。

## 7. 审校与交付

- 交付前检查标题层级、术语一致性、数据和链接有效性、代码与命令可复制性、图片与图注完整性。
- 删除过时内容、重复表述、占位符和无效链接；确认文档与当前实现或决策一致。
- 需要交付 PDF 时，遵循项目 `writing-standard` Skill 的 LaTeX 专项流程，使用 XeLaTeX 编译并核验输出；普通 Markdown 文档不强制转换为 PDF。

## 8. 语言风格

避免使用"口水词"或短语，比如结论里的"Bottom Line:"（归根结底）、"delve"（深入探讨）、"foster"（促进）、"leverage"（利用）、"it's worth noting"（值得注意的是）、"importantly"（重要的是）、"Question? Answer."（问题？答案。）、"This isn't about X. It's about Y."（这不是关于 X，而是关于 Y）、"genuinely"（真正地），以及连字符连接的复合描述和形容词。不要使用总结性结尾陈述，比如"In short:"（简而言之）、"The simplest mental model is:"（最简单的心智模型）。直接陈述要采取的行动。避免添加不会做什么、什么会保持不变，或者将如何分离或分类结果的说明。不要使用对比框架，比如"X, not Y"（X，而不是 Y）或"X—not Y"（X，而不是 Y），这会引入没有要求的、未经请求的替代选项。避免自造的复合标签，比如"exact-head checks"（精确头部检查）或"editorial-row layouts"（编辑行布局），避免模糊的限定词和陈词滥调的过渡；用平实的动词和介词直接陈述实际关系。

默认使用清晰、简洁的段落，每段展开一个核心观点。只有当信息确实是并列的、顺序的，或者更容易比较的时候才使用列表，避免嵌套列表，除非层级关系无法用文字清晰表达。使用平实、简单的语言：熟悉的词汇、具体的例子、精准的动词。优先使用主动语态和直接陈述。把核心观点清楚、尽早地说出来，然后用读者需要的解释和细节来展开。让每一句话都承接上一句。展开重要的观点，提供足够有用的支撑。用平实的语言代替行话，技术细节只在有助于向读者说明一个观点或一项工作的程度上才引用。以清晰、连贯的方式传达复杂概念，并根据工程师的提示和上下文所假设的背景知识水平来调整写作。
