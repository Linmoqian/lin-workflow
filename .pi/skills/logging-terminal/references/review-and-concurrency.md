# Review、前后端并发与验证（logging-terminal references）

## 7. Review 检查

代码 Review 时，至少检查：

- 是否使用语义输出而不是散落的颜色控制和临时打印。
- 是否正确区分终端输出与结构化日志。
- 是否满足 TTY、CI、重定向和非交互环境的稳定输出要求。
- 是否记录了必要的任务、阶段、结果和错误上下文。
- 是否存在敏感信息泄露、无限刷屏、未关闭的 Debug 输出或未限制的高频日志。

## 15. 前后端与并发约束

前端：

- 禁止散落 `console.log`、`console.warn`、`console.error` 作为正式日志；统一通过日志适配器或调试信息总线输出。
- 调试信息总线至少携带 `trace_id`、`operation_id`、`event` 和 `level`。
- 页面卸载、路由切换和取消操作必须结束或标记未完成的操作；IPC 失败必须保留前后端关联 ID。

Rust/Tauri：

- command 入口生成或接收 `trace_id`，服务层和异步任务继承日志上下文。
- 不在锁内、UI 线程或阻塞任务中执行慢速日志 I/O。
- 后台任务记录创建、开始、结束、取消、超时和回收结果；生产路径禁止用 `println!`、`dbg!` 替代日志。

并发与高频任务：

- 并发任务继承父操作上下文，但不同任务不得共用同一个 `operation_id`。
- 循环、轮询、进度、批处理和重试日志必须级别过滤、限频、采样或汇总。
- 采样事件附带采样率或汇总计数，不能影响 `warn`、`error`、`critical` 和失败终态日志。
- 日志写入器具备有界队列、背压和关闭刷新语义；应用退出前有限时间内完成刷新，超时记录未刷新的数量。
- 日志器异常不得反向导致业务崩溃，除非属于明确的安全审计要求。

## 16. 验证要求

日志功能至少验证：

- 事件字段完整性、字段命名和 JSON Lines 可解析性。
- `trace_id`、`operation_id`、父子操作和前后端传递。
- 开始到结束的状态转换、耗时、成功、失败、重试、取消、超时和资源受限区分。
- 错误来源链、稳定错误码和前端安全错误映射。
- 敏感字段、异常堆栈、路径、多行内容和日志注入的脱敏。
- 级别开关、采样、限频、队列满载、日志丢弃、轮转失败和退出刷新。
- TTY、CI、管道和重定向下的稳定终端输出。
- 日志写入故障不会阻塞或破坏主业务流程。

只报告实际执行的验证命令和结果；未执行的内容标记为“未验证”，不得用静态推断替代运行证据。
