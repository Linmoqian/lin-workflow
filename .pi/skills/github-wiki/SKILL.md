# GitHub Wiki 规范

## 1. 定位与权威关系

- GitHub Wiki 用于项目入门、使用教程、操作手册、架构说明、故障排查、FAQ 和贡献者导航。
- 正式工程规范、API 契约、架构决策、设计 Token、安全策略、代码 Review 报告和实验记录必须以主仓库（`docs/`、`.pi/skills/`）为唯一权威源；Wiki 只提供摘要和链接。
- Wiki 与主仓库内容冲突时，以当前代码、测试、主仓库规范和已批准的工程决策为准；发现冲突后应立即标记 Wiki 页面为“待更新”。
- Wiki 不替代 GitHub Release、变更日志或接口文档；版本发行信息仍以受保护的 `main`、Git Tag、Release 和仓库文档为准。

## 2. 权限与协作边界

- GitHub Wiki 是独立的仓库，通常位于 `<owner>/<repository>.wiki.git`；本项目推荐将它以 Git 子模块注册到主仓库的 `docs/wiki/`，而不是复制成普通目录。
- 子模块只在主仓库记录 Wiki 仓库的精确提交指针（gitlink）和 `.gitmodules` 配置；Wiki 的页面历史、分支和提交仍属于独立仓库。
- Wiki 写权限只授予维护人员或文档维护组；普通贡献者通过 Issue 或拉取请求提出修改建议。
- 正式页面禁止直接在网页编辑器中绕过审查；需要紧急修复时也必须保留原因、审查人和后续补审记录。
- Wiki 的拉取、提交、推送、发布、覆盖、删除和归档都属于远程或外部状态变更，必须取得工程师明确确认。
- 推荐工作流为：AI 起草或检查 → 人工 Review → 工程师确认 → 发布 Wiki。AI 不得自行获得 Wiki 写权限或发布凭据。
- 子模块注册必须在 Wiki 仓库地址、默认分支、权限和备份策略确认后进行；没有实际仓库地址时不得创建空的 `docs/wiki/` 或占位 `.gitmodules`。

## 3. 创建前规划

创建 Wiki 前必须完成以下检查：

1. 明确目标读者、使用场景、页面边界和成功标准。
2. 检索主仓库 `README.md`、`docs/`、Issue 和现有 Wiki，确认没有重复或冲突内容。
3. 为每个主题确定唯一权威源、维护人、适用版本和复审周期。
4. 只创建有实际内容和导航入口的页面，不创建空目录、空页面或无法维护的占位内容。
5. 预先规划 `Home`、`_Sidebar` 和必要的页面链接，避免发布孤立页面。

## 4. Wiki 初始化与子模块注册

Wiki 首次创建或迁移时按以下顺序执行：

1. 在仓库设置中确认 Wiki 已启用，并核对维护人员权限。
2. 在确认远程地址后，将 Wiki 仓库注册为子模块；不要直接复制页面或覆盖远程历史。

以下命令中的尖括号占位符必须替换为实际仓库信息后再执行：

```powershell
git submodule add https://github.com/<owner>/<repository>.wiki.git docs/wiki
git submodule update --init --recursive
git -C docs/wiki status --short
```

3. 在 `docs/wiki/` 内创建独立的本地工作分支，例如 `docs/wiki-initial`，完成页面编写和本地检查；不要在主仓库分支中直接改写子模块历史。
4. 先建立最小可用页面集合，再逐步补充专题内容。
5. 检查链接、代码块、命令、图片、版本信息、敏感信息和导航结构。
6. 由维护人员在子模块仓库内进行内容 Review，并记录未覆盖项、潜在风险和待办。
7. 工程师确认页面范围、子模块目标提交和发布内容后，才允许向 Wiki 远程仓库推送。
8. 子模块提交推送成功后，在主仓库检查 gitlink 变更和 `.gitmodules`，再提交新的子模块指针。
9. 发布后从干净环境执行 `git submodule update --init --recursive`，打开 `Home`、`_Sidebar` 和新增页面，确认导航、渲染和链接可用。

## 5. 子模块日常更新

更新 Wiki 必须先更新子模块自身，再更新主仓库指针：

```powershell
git -C docs/wiki fetch origin
git -C docs/wiki pull --ff-only
git -C docs/wiki status --short
```

完成页面 Review 后，在子模块仓库中提交并推送；随后回到主仓库执行：

```powershell
git diff --submodule=log -- docs/wiki
git add .gitmodules docs/wiki
git diff --cached --submodule=log
```

- 主仓库只提交 `.gitmodules` 和子模块提交指针，不把 Wiki 文件复制到主仓库提交中。
- 不得在未 Review 的情况下使用 `git submodule update --remote` 更新指针。
- 子模块未初始化、指针未推送或远程提交不可访问时，不得把主仓库指针发布给其他协作者。
- 子模块的提交信息遵循 Wiki 仓库已有规范；没有独立规范时，使用项目的 Conventional Commits 和单行一句话描述。

## 6. 克隆与协作者同步

首次克隆主仓库后必须初始化子模块：

```powershell
git clone <主仓库地址>
Set-Location <主仓库目录>
git submodule update --init --recursive
```

切换主仓库分支或拉取包含 Wiki 更新的提交后，应再次运行 `git submodule update --init --recursive`，确认 `docs/wiki/` 指向主仓库记录的精确提交。

## 7. 初始页面与导航

建议按实际内容逐步建立以下页面，不要求一次性全部创建：

| 页面 | 最低内容 | 是否通常需要 |
| --- | --- | --- |
| `Home` | 项目简介、状态、快速入口、版本和反馈入口 | 必须 |
| `getting-started` | 环境要求、安装、首次运行和验收方式 | 有可运行项目时必须 |
| `architecture` | 系统边界、模块关系、关键约束和权威设计文档 | 有架构说明时建立 |
| `development-guide` | 分支、构建、测试、Review 和本地验证入口 | 有协作开发时建立 |
| `operations` | 部署、监控、日志、回滚和权限边界 | 有运维流程时建立 |
| `troubleshooting` | 按症状组织的排查步骤、证据和修复条件 | 有已知问题时建立 |
| `faq` | 高频问题、适用版本和权威来源 | 问题达到复用价值时建立 |
| `glossary` | 术语、缩写、单位和领域定义 | 跨领域项目建议建立 |
| `_Sidebar` | 全站稳定导航 | 页面超过两个时建立 |
| `_Footer` | 许可证、反馈入口、适用版本和更新时间 | 对外 Wiki 建议建立 |

`Home` 和 `_Sidebar` 必须指向所有正式页面；已归档页面不得出现在现行导航中。

## 8. 页面命名与元信息

- 稳定 Wiki 页面使用小写 `kebab-case`，保持 URL 和内部链接稳定，例如 `getting-started`、`troubleshooting`。
- 稳定页面不强制使用日期前缀；页面顶部必须记录最后复审日期和适用版本。
- 会议记录、复盘、迁移报告和其他历史性页面使用 `YYYY-MM-DD-主题名`，并遵循项目写作规范。
- 禁止使用 `latest`、`new`、`final`、`final-final`、`today` 或无意义数字作为稳定页面名。
- 每个正式页面顶部应包含以下元信息表：

```markdown
| 项目 | 内容 |
| --- | --- |
| 状态 | 维护中 |
| 适用版本 | v0.1.x |
| 维护人 | 项目维护组 |
| 最后复审 | 2026-08-24 |
| 复审周期 | 每季度或相关功能变更时 |
| 权威来源 | `docs/example.md` |
```

状态只使用 `草稿`、`维护中`、`待更新`、`已弃用` 或 `已归档`。

## 9. 页面内容规范

每个操作型页面至少包含：目标与读者、前置条件、操作步骤、预期结果、失败处理、限制、权威来源和相关页面。

- 先给结论或任务目标，再给步骤、依据和例外；一个标题只表达一个主题。
- 命令、路径、配置项和版本号必须可复制，且注明适用操作系统、工具链和验证时间。
- 代码示例必须与当前 API、配置和项目结构一致；无法验证的示例必须明确标注未验证。
- 图片、截图和图表必须有准确的替代文本、来源和必要的版本或时间范围；不得用图片替代可复制正文。
- 外部链接应指向具体、稳定且有权限的来源；失效链接应在复审时修复或移除。
- 术语、单位、时间、坐标、状态和错误等级遵循项目专题规范，不在 Wiki 中重新定义一套口径。
- 多语言页面应使用稳定的语言后缀并相互链接；不要混合维护多个互相矛盾的译文。

## 10. Review 与发布前检查

Wiki 页面发布前至少检查：

- 内容与当前代码、配置、测试、发行版本和主仓库权威文档一致。
- 页面已加入 `Home`、`_Sidebar` 或相关页面，且不存在孤立入口。
- 命令、路径、版本号、环境变量和权限要求准确，能够在声明的环境中复现。
- 链接、代码块、表格、图片、替代文本和 Markdown 渲染正常。
- 没有 Token、API Key、密码、私钥、证书、个人信息、内部地址、未公开漏洞细节或未授权实验数据。
- 已标注适用版本、维护人、最后复审日期、已知限制和未验证项。
- 没有与现有页面重复、冲突、过时或无法维护的内容。
- 涉及安全、API、发行、硬件、机器人或实验流程时，已由对应领域负责人专项审查。

## 11. 更新、完善与复审

以下事件发生时必须更新相关 Wiki 页面：

- 代码、配置、API、依赖、工具链或部署流程变化。
- 新版本发布、兼容性变化、迁移方案或回滚策略变化。
- Issue、Review 或用户反馈发现错误、歧义或缺失步骤。
- 安全事件、隐私要求或权限边界变化。
- 页面达到复审周期；默认每季度复审一次，安装、部署、API 和安全页面应在相关变更后立即复审。

每次复审至少更新最后复审日期、适用版本、页面状态、变更摘要和已知限制。重大更新应保留 Wiki Git 提交历史，并在主仓库任务、Release 或变更日志中留下关联记录。

## 12. 弃用、归档与恢复

- 过时页面不得直接删除；先标记为 `已弃用` 或 `已归档`，说明原因、生效日期和替代页面。
- 从主导航移除归档页面，但保留历史链接、迁移说明和必要背景。
- 已归档页面不得被新页面作为现行操作依据引用。
- 只有法律、安全、隐私或凭据泄露等必须删除的情况，才可彻底移除页面；删除前必须获得工程师确认并记录原因、范围和恢复依据。
- 定期导出或保留 Wiki 源文件，避免独立 Wiki 仓库成为唯一备份。

## 13. 版本绑定与发行

- 安装、部署、API、迁移、兼容性和回滚页面应在对应版本发布前完成复审。
- 版本绑定页面必须关联 Git Tag、GitHub Release、适用版本、验证结果和已知限制。
- Wiki 发布不能代替 GitHub Release；正式发行仍遵循 [GitHub 规范](../github-workflow/SKILL.md) 的 Tag、制品和发布确认流程。
- 已发布版本的 Wiki 历史不得被改写为不兼容的内容；发现错误时追加修正记录并指向安全版本。

## 14. AI 使用边界

AI 可以搜索重复页面、生成草稿、检查链接和命令、提示可能过时的页面，以及生成 Review 清单。

AI 不得未经确认直接发布、删除、覆盖或归档页面，不得把推测内容写成已验证事实，不得承诺 API、命令或版本兼容性，也不得接触 Wiki 写入凭据。

## 15. 完成标准

Wiki 只有在以下条件全部满足后，才算完成创建或更新：

1. 读者、页面边界和唯一权威源已明确。
2. `Home`、导航和正式页面之间无孤立链接。
3. 元信息、版本、维护人和复审日期完整。
4. 命令、链接、图片、渲染和敏感信息检查通过。
5. 相关领域 Review、未覆盖项和潜在风险已记录。
6. 工程师已确认发布范围、目标仓库和远程操作。
7. 发布后已从干净环境初始化子模块并验证首页、导航和关键页面。
