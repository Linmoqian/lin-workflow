# GitHub Wiki 规范

## 1. 定位与权威关系

- GitHub Wiki 用于项目入门、使用教程、操作手册、架构说明、故障排查、FAQ 和贡献者导航。
- 正式工程规范、API 契约、架构决策、设计 Token、安全策略、代码 Review 报告和实验记录必须以主仓库（`docs/`、`.pi/skills/`）为唯一权威源；Wiki 只提供摘要和链接。
- Wiki 与主仓库内容冲突时，以当前代码、测试、主仓库规范和已批准的工程决策为准；发现冲突后应立即标记 Wiki 页面为“待更新”。
- Wiki 不替代 GitHub Release、变更日志或接口文档；版本发行信息仍以受保护的 `main`、Git Tag、Release 和仓库文档为准。

## 2. 权限与协作边界

- GitHub Wiki 是独立的仓库，通常位于 `<owner>/<repository>.wiki.git`；本项目推荐将它以 Git 子模块注册到主仓库的 `docs/wiki/`，而不是复制成普通目录。
- 子模块只在主仓库记录 Wiki 仓库的精确提交指针（gitlink）和 `.gitmodules` 配置；Wiki 的页面历史、分支和提交仍属于独立仓库。
- Wiki 写权限只授予维护人员或文档维护组；普通贡献者通过 Issue 或拉取请求提出修改建议。
- 正式页面禁止直接在网页编辑器中绕过审查；需要紧急修复时也必须保留原因、审查人和后续补审记录。
- Wiki 的拉取、提交、推送、发布、覆盖、删除和归档都属于远程或外部状态变更，必须取得工程师明确确认。
- 推荐工作流为：AI 起草或检查 → 人工 Review → 工程师确认 → 发布 Wiki。AI 不得自行获得 Wiki 写权限或发布凭据。
- 子模块注册必须在 Wiki 仓库地址、默认分支、权限和备份策略确认后进行；没有实际仓库地址时不得创建空的 `docs/wiki/` 或占位 `.gitmodules`。

## 3. 创建前规划

创建 Wiki 前必须完成以下检查：

1. 明确目标读者、使用场景、页面边界和成功标准。
2. 检索主仓库 `README.md`、`docs/`、Issue 和现有 Wiki，确认没有重复或冲突内容。
3. 为每个主题确定唯一权威源、维护人、适用版本和复审周期。
4. 只创建有实际内容和导航入口的页面，不创建空目录、空页面或无法维护的占位内容。
5. 预先规划 `Home`、`_Sidebar` 和必要的页面链接，避免发布孤立页面。


## 4. 按需细读与完成标准

- 子模块注册、日常更新、克隆与协作者同步：[submodule-workflow.md](references/submodule-workflow.md)，执行相应 Git 操作时读。
- 初始页面与导航、页面命名与元信息、内容规范：[page-conventions.md](references/page-conventions.md)，创建或修改页面时读。
- Review 与发布前检查、复审、弃用归档、版本绑定：[review-and-lifecycle.md](references/review-and-lifecycle.md)，发布或治理 Wiki 时读。

## 14. AI 使用边界

AI 可以搜索重复页面、生成草稿、检查链接和命令、提示可能过时的页面，以及生成 Review 清单。

AI 不得未经确认直接发布、删除、覆盖或归档页面，不得把推测内容写成已验证事实，不得承诺 API、命令或版本兼容性，也不得接触 Wiki 写入凭据。

## 15. 完成标准

Wiki 只有在以下条件全部满足后，才算完成创建或更新：

1. 读者、页面边界和唯一权威源已明确。
2. `Home`、导航和正式页面之间无孤立链接。
3. 元信息、版本、维护人和复审日期完整。
4. 命令、链接、图片、渲染和敏感信息检查通过。
5. 相关领域 Review、未覆盖项和潜在风险已记录。
6. 工程师已确认发布范围、目标仓库和远程操作。
7. 发布后已从干净环境初始化子模块并验证首页、导航和关键页面。
