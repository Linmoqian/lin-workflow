# 项目工程规范

使用本 Skill 完成仓库内的工程改动。将仓库根目录视为本文件的三级父目录。

## 读取规范

1. 遵循仓库根目录 [AGENTS.md](../../../AGENTS.md) 的通用约束与红线。
2. 涉及具体技术栈、流程或工具时，按需读取 `.pi/skills/` 下对应专题 Skill 的 `SKILL.md`，例如 `cpp-dev`、`python-dev`、`verification`、`git-workflow`、`dependency-management`、`external-tools`、`windows-environment`。
3. 查找当前目录及子目录中的更具体规范；其优先级高于通用规范。

## 根目录布局

* `app/` 存放项目主体代码。
* `docs/` 存放开发文档和开发日志；`docs/wiki/` 是 GitHub Wiki 子模块挂载点（仅在仓库地址确认后创建）；`docs/api/`、`docs/review/` 按需存放实际接口文档与 Review 报告，不创建空目录。
* `.githooks/` 存放版本控制的 Git 提交钩子；克隆后运行 `.githooks/setup.ps1` 启用。
* `.pi/skills/` 存放全部工程规范 Skill；`.pi/agents/` 存放子代理定义。
* `tests/` 存放跨技术栈测试和验收测试；语言工具链约定的测试放在对应 crate 或模块内。
* `overview/` 与 `.overview/` 存放项目数字孪生地图。
* 按功能分类、按模块划分子目录，避免在根目录堆积文件；子目录附带简短 `README.md`、必要的 `.gitignore` 与 `.env.example`。
* 迁移或重命名现有目录前，必须先获得工程师同意。

## 实施流程

1. 说明目标、成功标准、修改范围与不修改范围。复杂任务给出不超过三步的计划。
2. 运行 `git status --short` 并检查相关差异。将已有未提交改动视为工程师的工作，禁止覆盖、回滚、格式化或混入提交。
3. 先复用项目已有实现、依赖、包管理器、测试和构建流程；只有在确有必要时新增依赖或工具。
4. 搭建工程、模块或配置时，优先使用对应官方 CLI、脚手架、模板和代码生成器，不从零手写；官方方案不适用或不可用时，记录原因并验证自建方案。
5. 实现非平凡能力前，先探索项目已有依赖、官方生态和维护活跃的社区开源方案，评估功能、许可证、安全、兼容性、性能和迁移成本；可复用或适配时避免重复开发，自研需记录未采用理由。
6. 采用最小可验证改动，不顺手重构、升级无关依赖或扩展需求；发现无关问题可以汇报，但不得擅自修改。
7. 根据改动类型执行相应验证，并如实记录实际结果。
8. 维护 [TODO.md](../../../TODO.md)：任务完成后标记完成，不删除历史事项。

## 项目记录

* `TODO.md` 保持简洁，完成项标记完成而不删除。
* `MEMORY.md` 只在工程师明确要求、任务需要跨会话维护或项目确有长期协作需求时创建；只记录长期有效的架构决策、技术约束和流程，不记录临时任务、密钥、账号、私人路径或敏感部署信息。
* 项目 Overview 地图的维护遵循 `overview-maintenance` Skill；代码、任务、架构、风险或验收状态变化后及时更新，避免与真实项目状态脱节。
* 正式架构决策进入 ADR 或设计文档，不用 `MEMORY.md` 代替。

## 决策边界

遇到不可逆操作、重要数据迁移、外部接口或持久化格式变更、重大依赖引入、发布部署、敏感信息处理，或无法安全保留已有改动时，暂停并询问工程师。

对于局部且可逆的实现细节、可由现有测试快速验证的选择，或明显符合现有风格的方案，声明简短假设后继续。

## 验证选择

* 行为、构建、依赖、配置、数据格式和 UI 改动必须验证；浏览器前端改动需要截图验证。
* 可逆、低影响的变更不写与实现重复的测试；测试编写与运行原则遵循 `verification` Skill。
* 没有可用自动化脚本时提供可复现的手动步骤，并如实说明未完成自动化验证的范围。
* 纯说明文字、拼写或不参与执行的注释改动可免完整测试，但必须检查差异、链接与示例。
* 只报告实际运行过的验证；未运行或失败时说明原因和未覆盖范围。

## 工具与兼容性

* 库文档查询、复杂文档解析与文献检索遵循 `external-tools` Skill；依赖与环境管理遵循 `dependency-management` Skill；Windows 命令与路径处理遵循 `windows-environment` Skill。
* 终端输出同时提供文字状态标识，例如 `[成功]`、`[警告]`、`[错误]`；CI、重定向或设置 `NO_COLOR` 时关闭颜色。

## 提交与汇报

允许自主创建本地提交并保持高频节奏；仅在独立、可验证且适合保留的语义单元完成后提交。提交前确认：改动可与已有工作区区分、完成最小验证、暂存区不含敏感或无关文件，`.githooks/` 已启用并通过。提交信息使用中文 Conventional Commits，一行一句话高度概括本次提交的唯一目的，例如 `fix(scope): 修复具体问题`，不包含任何暗示由 AI 生成的字样。推送远程仓库必须取得工程师明确同意。

最终汇报改动、实际验证、提交信息、未解决风险和过程中发现的技术问题；没有运行测试或没有提交时明确原因。
