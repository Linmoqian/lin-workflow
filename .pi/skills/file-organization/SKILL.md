# 文件层级组织规范

## 1. 根目录布局

* `app/` 存放项目主体代码。
* `docs/` 存放开发文档和开发日志；`docs/wiki/` 是 GitHub Wiki 子模块挂载点（仅在仓库地址确认后创建）；`docs/api/`、`docs/review/` 按需存放实际接口文档与 Review 报告，不创建空目录。
* `.githooks/` 存放版本控制的 Git 提交钩子；克隆后运行 `.githooks/setup.ps1` 启用。
* `.pi/skills/` 存放全部工程规范 Skill；`.pi/agents/` 存放子代理定义。
* `tests/` 存放跨技术栈测试和验收测试；语言工具链约定的测试放在对应 crate 或模块内，例如 Rust Cargo 集成测试放在 `app/src-tauri/tests/`。
* 新增文件按上述结构放置；迁移、重命名或删除现有目录前必须取得工程师同意。

## 2. 层级组织原则

- 按功能分类、按模块划分子目录，保持清晰的层级结构；一个目录只承载一类职责。
- 避免在根目录堆积文件；根目录只保留入口配置（如 `AGENTS.md`、`TODO.md`、`README.md`、`package.json`）与无法归属子目录的顶层产物。
- 目录深度以能定位为限，不为单一文件创建多层嵌套；同类文件数量增长时先聚拢到模块目录，再考虑细分。
- 子目录需要附带简短 `README.md`（说明职责与内容）、必要的 `.gitignore`（忽略该目录特有产物）与 `.env.example`（该目录涉及环境变量时提供示例，开发阶段用 `.env` 加载）。
- 不创建空目录、占位目录或为未来需求预留的结构；目录随实际内容产生。

## 3. 命名约定

- 目录名使用小写 kebab-case，语义稳定、可预测，不使用空格、中文与下划线。
- 代码文件名遵循对应语言规范：Python 用 `snake_case`，JavaScript/TypeScript 组件与模块按项目前端规范，Rust 按 crate 惯例。
- 文档文件名以 `YYYY-MM-DD-主题名` 开头，细则遵循 `writing` Skill。
- 同一概念的名称在目录、文件与代码模块间保持一致。

## 4. 文件归属判断

新增文件时按顺序判断归属：

1. 项目主体代码 → `app/` 对应模块。
2. 跨技术栈或验收测试 → `tests/`；语言工具链测试 → 语言约定位置。
3. 开发文档、日志、报告 → `docs/` 对应子目录。
4. 可复用工程规范 → `.pi/skills/<skill-name>/SKILL.md`，一个语义单元一个目录。
5. 顶层配置与入口 → 根目录，仅限必要项。

无法明确归属时先询问工程师，不自行创建新顶层目录。

## 5. 迁移与清理

- 迁移、重命名或删除现有目录前必须取得工程师同意，并同步更新仓库内所有引用路径。
- 只清理本次改动产生的孤立文件与空目录；不顺手整理无关结构。
- 迁移后全仓库检索旧路径，确认无残留引用再提交。
