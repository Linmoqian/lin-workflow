# 危险分析与安全设计细则（system-safety references）

## 3. 危险分析与安全论证

在设计、硬件变化、模型变化、部署环境变化和重大软件变更前执行危险分析：

1. 列出危险源、危险事件、暴露人员、触发条件和后果。
2. 评估严重度、发生概率、可避免性或项目采用的等价风险维度。
3. 为不可接受风险分配安全需求、预防措施、检测措施和缓解措施。
4. 将每条安全需求映射到设计、实现、测试和证据。
5. 记录残余风险、假设、责任人、接受人和复审日期。

可使用 FMEA、故障树（FTA）、事件树、危害日志或等效方法，但必须记录版本、范围、假设和结论。模型、传感器、通信、供电、执行器、人因、环境和第三方依赖必须纳入分析；不得只分析正常软件路径。

## 4. 安全状态与状态转换

至少定义以下状态及其进入、退出和允许动作：

| 状态 | 含义 | 典型允许动作 |
| --- | --- | --- |
| `normal` | 正常任务运行 | 受约束的任务动作 |
| `degraded` | 功能受限但仍可控 | 降速、降载或有限任务 |
| `protective_stop` | 检测到风险，停止危险动作 | 诊断、人工确认、受限复位 |
| `emergency_stop` | 紧急停止，保持锁定 | 仅允许安全复位流程 |
| `fault` | 故障待处理 | 记录、隔离、维护 |
| `maintenance` | 授权维护状态 | 受控诊断和维修动作 |

- 状态转换必须由明确事件触发，并记录来源、时间、原因和结果。
- 保护停止和急停不得自动恢复危险运动；恢复前重新检查人员、设备、传感器、限位和任务状态。
- 复位是幂等操作，必须避免重复上电、重复动作或恢复过期命令。
- 安全状态的失效保护方向必须明确：看门狗、通信中断、供电异常、控制器崩溃和安全监督失联时进入哪个状态。

## 5. 急停、保护停机与物理防护

- 急停必须有独立、可触达、可测试的硬件路径；软件按钮不能替代硬件急停，除非风险分析明确允许并有等效防护。
- 急停应切断或抑制危险能量，控制制动、继电器、驱动器使能、保持力和惯性运动，并验证停止时间和停止距离。
- 急停信号应具备冗余、监测、锁存和防误复位设计；复位不得自动重新启动危险动作。
- 保护停机用于可控的风险降级，急停用于需要立即停止或无法保证可控减速的危险情况；两者不可混用。
- 软件安全监督、硬件限位、机械限位、护栏、联锁和电源隔离各自的作用与失效模式必须记录。
- 每次运行前检查急停、限位、制动、护罩、联锁、看门狗和安全输入；测试结果可追溯。

## 6. 安全约束与运行时监控

- 所有运动命令通过集中安全监督，校验速度、加速度、力、力矩、功率、温度、载荷、工作空间、碰撞距离和命令有效期。
- 约束使用安全默认值和上限；配置变更需权限、版本和审计记录，禁止运行时无审计地放宽限制。
- 传感器数据过期、冲突、越界、失真或质量不足时，进入明确的降级或停止状态。
- 通信心跳、控制反馈、执行器响应、供电、温度、内存、任务和时钟同步必须有超时和失效行为。
- 模型或规划器输出必须经过规则、几何、动力学和安全约束检查；模型置信度不能单独作为安全证明。
- 安全监控自身必须有健康检查、看门狗、故障注入和失联处理，不能只监控被控对象。

## 7. FMEA 与故障树要求

FMEA 至少包含：组件或功能、失效模式、原因、局部影响、系统影响、检测方式、安全响应、严重度、发生概率、可检测性、责任人和验证证据。

故障树至少：

- 顶事件定义为明确的危险结果，而不是“系统异常”。
- 使用可审查的逻辑门、基本事件、公共原因和独立性假设。
- 分析传感器失效、执行器卡滞、软件错误、时钟异常、通信丢失、供电异常、人因和环境因素。
- 对单点故障、潜伏故障、共因故障和故障组合给出检测或缓解方案。
- 任何“不会发生”“不可能同时发生”或“由操作员处理”的假设都要记录证据和边界。

FMEA/FTA 的结论必须转化为代码、配置、硬件或操作需求，并进入测试与 Review 清单。
