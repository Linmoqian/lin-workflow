# 科研工作流

使用本 Skill 把一个研究想法推进为可核验的研究交付物。研究者保留问题定义、实验设计、科学判断、核心结论和最终责任；Agent 负责整理材料、执行明确的机械工作、暴露证据缺口并保持可追溯记录。

## 1. 启动前读取规范

先读取根目录 `AGENTS.md`、`CLAUDE.md` 和 `TODO.md`。根据任务实际范围读取专题规范，不得凭记忆替代规范：

- 写作或论文交付：[写作规范](../../../docs/development/writing.md)和项目 `writing-standard` Skill。
- 数据、实验或生物样本：[数据与实验规范](../../../docs/development/data-experiment.md)。
- 训练、评测或推理：[机器学习规范](../../../docs/development/ml.md)。
- 机器人、控制、传感器或执行器：[具身智能与机器人规范](../../../docs/development/robotics.md)。
- 仿真、回放或 HIL：[仿真与硬件在环规范](../../../docs/development/simulation.md)。
- 数值、坐标、姿态或时间戳：[单位、坐标与时间规范](../../../docs/development/units-coordinate-time.md)。
- 高风险设备、人体或现场运行：[系统安全规范](../../../docs/development/safety.md)。
- 需要审查或验收：[代码 Review 规范](../../../docs/development/code-review.md)和[验证规范](../../../docs/development/verification.md)。

如果任务同时涉及代码、接口、日志、并发、C++、嵌入式、Python、Rust、CMake 或 HarmonyOS，再读取对应专题规范。发现当前目录有更具体的规则时，先读取并遵守它。

## 2. 研究边界与证据原则

1. **研究者拥有科学判断。** Agent 可以提出问题、对比方案和指出风险，但不得未经确认替研究者决定研究问题、因果解释、创新性或发布结论。
2. **证据强度限制结论强度。** 明确区分事实、计算结果、推断、计划、假设和未验证项；证据不足时降低措辞、补充检索、改写或删除，不用“看起来合理”填空。
3. **禁止制造证据。** 不编造论文、引用、数据、实验结果、样本、指标、参数、图表、设备行为或具体案例。无法核验的引用不进入正式交付物。
4. **保留失败和不确定性。** 失败实验、负结果、异常批次、未达到门槛的评测和人工接管不能静默删除；记录原因、影响和后续处理。
5. **先冻结口径再执行。** 研究问题、样本单位、变量、指标、数据划分、停止条件和安全边界在执行前确定；执行后不得为了结果随意改口径。
6. **每个结果可回溯。** 结果必须关联数据版本、代码提交、配置、环境、硬件或模型、随机种子、运行 ID 和验证命令。
7. **安全与伦理优先。** 涉及人体、动物、隐私、生物数据、动力设备或高能量执行器时，未完成必要审批和风险评估前不得开展或扩大实验。

## 3. 模式路由

先判断当前主要模式；混合任务按表中顺序串联，避免在没有研究简报时直接写结论。

| 模式 | 触发情况 | 主要交付物 | 必须读取 |
| --- | --- | --- | --- |
| 问题评估 | 只有想法、方向或候选问题 | 研究简报、可行性与风险清单 | 数据/安全/相关领域规范 |
| 文献调研 | 需要状态地图、关键工作或证据 | 检索记录、证据表、综合报告 | 写作规范、相关领域规范 |
| 实验设计 | 需要确定数据、对照、指标或方案 | 实验协议、运行清单模板、验收门槛 | 数据与实验、验证、单位时间 |
| 执行与分析 | 已有数据、运行或模型结果 | 数据血缘、质量报告、统计与失败分析 | 数据与实验、机器学习、日志 |
| 论文/报告 | 需要把已确认材料写成文稿 | 结构化 Markdown、LaTeX 或 PDF | 写作、数据/实验、模型规范 |
| 审查与投稿 | 需要交付前检查 | 问题清单、风险、修复优先级 | Review、验证、安全和写作 |

## 4. 标准流程

### 4.1 冻结研究简报

开始检索或实验前，创建简短的研究简报，至少写明：

- 研究对象、背景和明确的 2～3 个可回答研究问题（RQ）。
- 目标读者、预期交付物和不在范围内的内容。
- 假设、主要终点、次要终点、比较基线和成功/失败判定。
- 数据、设备、模型、时间和资源限制；涉及安全时写出禁止动作。
- 需要人工确认的决策点、当前已知证据和主要不确定性。

问题过于宽泛、目标互相冲突或缺少关键边界时，先提出最少的澄清问题；不能用默认假设掩盖会改变结论的歧义。

### 4.2 构建证据链

将每个重要主张拆成“主张 → 证据 → 推理 → 限制”，并保存证据台账。文献或外部事实的检索应：

1. 先围绕每个 RQ 设计关键词和至少两个互补视角，例如主流结果、反例/批评、相邻领域、方法学或应用限制。
2. 优先使用原始论文、官方文档、标准、数据集说明和可核验的实验记录；来源、版本、访问日期和链接一并保存。
3. 对引用核验作者、标题、年份、来源和主张是否真的由原文支持；只看到摘要时，不把全文细节写成事实。
4. 区分相关性与因果性、观察结果与解释、报告值与本项目复算值；冲突证据并列呈现并说明条件。
5. 记录未找到证据的方向和检索边界；“未检索到”不等于“不存在”。

需要实时或精确外部事实时，使用检索工具并在交付物中保留来源。没有检索能力时，只使用用户提供且可核验的材料，并明确能力降级。

### 4.3 设计实验与验收

实验协议在运行前确定：样本或试验单元、纳入/排除条件、对照、随机化或分组、变量、采样与时间语义、单位和坐标系、统计方法、最小样本量（如适用）、停止条件、异常处理和安全状态。

- 数据集使用不可变 `dataset_id` 和版本；原始数据只读，派生结果不能覆盖上游。
- 训练、验证、测试或实机/仿真边界在执行前冻结；按受试者、设备、场景或时间分组时，记录分组规则。
- 质量门槛、主要指标、失败切片、资源上限、延迟、功耗和人工接管条件必须可计算。
- 机器人和嵌入式实验必须先在低能量、隔离或仿真环境验证，再按安全批准逐级放量。
- 单位、坐标、时间戳、校准和同步误差作为接口契约，不使用无说明的数值。

### 4.4 执行、记录与复现

每次采集、处理、训练、仿真或评测创建唯一 `run_id`，并记录：

```text
输入数据及校验和
代码提交与脚本路径
配置、依赖锁文件和随机种子
操作系统、解释器/编译器、驱动、硬件和模型版本
开始/结束时间、时区、时钟基准和资源消耗
日志关联 ID、输出校验和、成功/失败状态及失败原因
```

运行目录和文档使用项目日期命名规范。禁止使用 `latest` 作为唯一版本，禁止手工修改派生数据而不留下前后校验和、原因和影响范围。重跑应产生新运行 ID；发现泄漏、配置错误或数据质量问题时冻结受影响结果，不只改最终数字。

### 4.5 分析与结论

分析前先执行数据质量、划分隔离、预处理一致性、单位/坐标/时间、异常值和权限检查。交付结果至少包含：

- 总体指标、有效样本数、排除数、分组或场景切片、失败类型和不确定性。
- 与可追溯基线的比较，以及指标定义、统计口径、阈值和适用边界。
- 探索性分析与预先计划的确认性分析的明确区分。
- 负结果、失败样本、异常运行、资源不足、超时、拒答、越界和人工接管统计。
- 结论、证据、限制和未验证项一一对应；不把相关性写成因果性，不把仿真通过写成实机安全证明。

结果文件不能只有图片；保留生成图表所需的结构化数据、脚本、配置和图注。图表中的每个数字都能追溯到数据版本和计算步骤。

### 4.6 写作与交付

根据读者选择 Markdown、LaTeX 或 PDF；遵循[写作规范](../../../docs/development/writing.md)和 `writing-standard` Skill。正式文稿至少包含：研究问题与范围、方法和数据、结果、限制、复现入口、伦理/安全说明（适用时）和参考文献。

写作时建立主张—证据矩阵：

| 主张 | 来源/运行 ID | 证据状态 | 限制 | 允许的措辞 |
| --- | --- | --- | --- | --- |
| 事实或观察 | 文献、数据或运行清单 | 已核验/待核验 | 适用范围 | 与证据强度相称 |
| 推断或解释 | 事实 + 推理链 | 有依据/待验证 | 替代解释 | 使用“可能、提示、与…一致” |
| 计划或预期 | 实验协议 | 未执行 | 需完成的验证 | 不写成已取得结果 |

引用、公式、图表、代码、数据和链接在交付前逐项核验。LaTeX 或 PDF 交付时同时保留权威源和可复现编译命令，不把 PDF 作为唯一事实源。

### 4.7 Review 与归档

交付前至少进行两轮检查：

1. **证据审查：** 研究问题是否得到回答，主张是否有来源，引用是否真实，结果是否与实验记录一致，失败与限制是否披露。
2. **工程审查：** 数据血缘、版本绑定、划分泄漏、单位/坐标/时间、日志、权限、资源、并发、测试、安全状态和回滚是否满足专题规范。

按 [代码 Review 规范](../../../docs/development/code-review.md) 在 `docs/review/YYYY-MM-DD-code-review-主题名.md` 记录仓库问题、潜在风险、证据、未覆盖范围和修复优先级。研究交付物归档时保留研究简报、协议、运行清单、数据/模型清单、结果、报告和验证记录；不提交受限原始数据或凭证。

## 5. AI 使用边界

允许 Agent 协助：

- 把宽泛想法整理成研究问题、方案选项和风险清单；
- 设计检索策略、整理用户提供或已核验的文献；
- 生成实验记录模板、数据处理代码、测试夹具和图表脚本；
- 检查结构、术语、引用格式、可复现步骤和语言表达；
- 按用户确认的材料起草论文或报告草稿。

禁止 Agent：

- 凭模型记忆捏造引用、数据、结果、实验过程、设备能力或法规要求；
- 为追求显著性而改动样本、指标、划分、排除规则或统计口径；
- 代替研究者决定核心创新、因果解释、安全放行或伦理结论；
- 隐藏失败、未验证项、AI 参与、数据来源或实验证据缺口；
- 将未经核验的生成内容直接提交、发布或用于控制危险设备。

每次 AI 辅助交付前，研究者必须对事实、代码、数据、结果、引用、图表和适用的 AI 披露要求进行最终确认。无法确认时，交付物标记为草稿或未验证，不写成正式结论。

## 6. 输出格式

根据任务选择最小必要交付物：

```text
研究简报：research-brief.md
证据台账：evidence-ledger.md 或 evidence-ledger.csv
实验协议：protocol.md
运行清单：run-manifest.json
结果与限制：results.md
主张—证据矩阵：claim-evidence-matrix.md
Review 报告：docs/review/YYYY-MM-DD-code-review-主题名.md
```

不要为了形式创建空目录或无内容模板。若任务只需要回答一个局部问题，直接给出局部结果并说明未覆盖范围；只有需要跨阶段协作或后续复现时才创建完整工作文件。

## 7. 完成判定

只有同时满足以下条件，才能把研究任务标记为完成：

- 研究问题、范围、输入和交付物明确；
- 关键主张有可核验来源或运行证据；
- 数据、代码、配置、环境、模型/硬件和结果可以关联；
- 失败、限制、风险和未验证范围已明确记录；
- 适用的测试、统计、伦理、安全和 Review 检查已完成；
- 交付格式、日期命名、链接、图表、引用和复现步骤已核验。

不满足任一项时，说明阻塞原因和下一步，不以完整叙述或漂亮图表掩盖证据缺口。
